    \begin{center}
        {\large \textbf{ABSTRACT}}
    \end{center}

    \vspace{0.3cm}
    In modern enterprise environments, supply chain operations often face severe delays due to fragmented record-
  keeping, unverified vendor credentials, off-contract spending, and subjective supplier reviews. Traditional
  procurement methods rely heavily on manual spreadsheets, unstructured email exchanges, and paper-based tracking.
  These practices lack real-time visibility, create compliance risks under tax regulations such as GST, and introduce
  coordination errors between buyers and external suppliers.

    To resolve these challenges, this project presents VendorFlow, an end-to-end procurement and supplier lifecycle
  management system built on the MERN stack (MongoDB, Express.js, React, Node.js). VendorFlow establishes a
  centralized platform with role-based access for three distinct users: Administrators, Procurement Buyers, and
  Vendors. Administrators manage supplier onboarding, inspect tax credentials like PAN and GSTIN, and approve high-
  value orders. Buyers draft purchase orders, calculate taxes, and evaluate vendor performance. Vendors receive
  incoming orders, track order fulfillment, and submit commercial invoices.

    A key feature of the system is a deterministic Finite State Machine that manages the purchase order lifecycle
  across sequential stages from draft creation to final closure. Each stage requires proper authorization, line-item
  verification, and automated 18 percent GST calculation. In addition, the platform includes a quantitative vendor
  evaluation module that scores suppliers across delivery timeliness, product quality, pricing, and customer support.
  Based on these scores, vendors are classified into performance tiers such as Preferred, Approved, On-Watch, or
  Blacklisted to help organizations make data-driven purchasing decisions.

    Security is maintained through JSON Web Token authentication stored in secure cookies, role-gated API endpoints,
  and an append-only audit trail that logs sensitive actions. VendorFlow provides an efficient, transparent, and
  structured procurement workflow that reduces manual effort, prevents unauthorized purchases, and improves supply
  chain reliability.

    \vspace{0.4cm}
    \noindent \textbf{1.1 \hspace{0.2cm} OVERVIEW}

    \vspace{0.25cm}
    In contemporary enterprise ecosystems, the efficient management of procurement and supplier lifecycles represents
  a critical determinant of operational continuity and financial solvency. While modern organizations have extensively
  automated customer-facing transactions and sales pipelines, internal procurement operations frequently remain
  fragmented and technologically neglected. Conventional commercial purchasing workflows, which historically relied on
  physical paper requisitions, uncoordinated telephonic agreements, or decentralized manual spreadsheets, fail to
  deliver real-time transparency and transactional certainty. Consequently, this work presents VendorFlow, an
  automated, enterprise-grade Procurement and Supplier Lifecycle Management System engineered using the MERN (MongoDB,
  Express.js, React 19, Node.js) technology stack. By synergistically combining a deterministic transactional state
  machine, automated statutory tax calculations, algorithmic performance evaluations, and role-based access control,
  the proposed platform transforms chaotic, reactive purchasing routines into a streamlined, high-trust digital
  utility.

    \vspace{0.4cm}
    \noindent \textbf{1.2 \hspace{0.2cm} PROBLEM DEFINITION}

    \vspace{0.25cm}
    Effective enterprise purchasing relies fundamentally upon data accuracy, regulatory verification, and transparent
  commercial coordination. However, institutions face severe operational challenges during day-to-day procurement due
  to isolated, manual record-keeping practices that introduce critical delays and financial leakage. When purchasing
  records are scattered across disconnected spreadsheets, organizations experience frequent duplicate requisitions,
  discrepancies between invoice values and agreed quotations, and complete loss of transactional auditability.

    Furthermore, manual workflows expose enterprises to significant statutory and financial risks. Verifying supplier
  Know-Your-Customer (KYC) documentation, including Goods and Services Tax Identification Numbers (GSTIN) and
  Permanent Account Numbers (PAN), through unstructured email exchanges often leads to missed verifications, invalid
  tax filings, and denied Input Tax Credits (ITC). Additionally, the absence of an enforced workflow permits unvetted
  off-contract purchases (maverick spend), while vendor contract renewals continue to rely on subjective anecdotal
  opinions rather than quantifiable performance records. To resolve these challenges, a centralized, role-gated
  platform is necessary to eliminate operational friction and ensure corporate governance.

    \vspace{0.4cm}
    \noindent \textbf{1.3 \hspace{0.2cm} OBJECTIVE}

    \vspace{0.25cm}
    The primary objective of this project is to research, architect, and develop VendorFlow---a robust, modular
  procurement management system that guarantees transactional transparency, regulatory compliance, and data-driven
  supplier oversight. The specific sub-objectives driving this development are outlined as follows:

    \begin{itemize}
        \item[*] \textbf{Role-Based Authentication Engine:} To implement a secure, Zero-Trust authentication
  architecture utilizing JSON Web Tokens (JWT) and encrypted \texttt{httpOnly} session cookies, strictly partitioning
  access privileges across Administrators, Buyers, and Suppliers.
        \item[*] \textbf{Automated KYC Onboarding Pipeline:} To design a multi-step onboarding workflow that validates
  statutory business credentials (PAN, GSTIN) and supports multi-file document uploads subjected to administrative
  review queues.
        \item[*] \textbf{Deterministic Purchase Order State Machine:} To model and enforce an eight-stage
  transactional Finite State Machine (FSM) governing order lifecycles (\textit{Draft $\rightarrow$ Pending Approval
  $\rightarrow$ Approved $\rightarrow$ Sent $\rightarrow$ Acknowledged $\rightarrow$ Delivered $\rightarrow$ Invoiced
  $\rightarrow$ Closed}), preventing unauthorized state leaps.
        \item[*] \textbf{Automated Line-Item and Tax Aggregation:} To develop a real-time financial computation
  routine that automatically aggregates itemized quantities, unit prices, sub-totals, and statutory 18\% GST additions,
  eliminating manual calculation errors.
        \item[*] \textbf{Quantitative Vendor Tier Classification:} To engineer a multi-pillar mathematical evaluation
  model that scores vendors across delivery timeliness, product quality, pricing, and support, autonomously mapping
  them into operational tiers (\textit{Preferred, Approved, On-Watch, Blacklisted}).
        \item[*] \textbf{Immutable Audit Trail Architecture:} To construct an append-only logging system that captures
  user identities, network metadata, and before-and-after state diffs on all critical operational transitions.
    \end{itemize}

    \vspace{0.4cm}
    \noindent \textbf{1.4 \hspace{0.2cm} SCOPE OF THE PROJECT}

    \vspace{0.25cm}
    This project centers on the comprehensive end-to-end development of the VendorFlow framework, integrating full-
  stack web software engineering with scalable document storage to deliver accurate and actionable procurement
  management. The scope encompasses several critical operational phases:

    \begin{itemize}
        \item[*] \textbf{Data Architecture and Storage:} The design and implementation of optimized MongoDB BSON
  schemas with compound indexing and virtual references to ensure sub-second query retrieval for vendors, purchase
  orders, evaluations, and audit logs.
        \item[*] \textbf{Core Workspace Module Development:} The construction of isolated, role-specific interfaces
  for Administrators (governance, KYC approvals), Procurement Buyers (order drafting, supplier reviews), and Vendors
  (order acknowledgement, fulfillment, invoicing).
        \item[*] \textbf{Lifecycle State Machine Execution:} The implementation of strict server-side transition
  guards and visual timeline steppers that prevent illegal order progressions and display milestone timestamps.
        \item[*] \textbf{Supplier Evaluation and Analytics:} The creation of dynamic performance graphs, multi-
  criteria radar visualizations, and categorized budget allocation analytics for strategic procurement planning.
    \end{itemize}

    \noindent \textit{Boundary Exclusions:} Real-time integration with external banking automated clearing houses
  (ACH) for direct fund disbursements and hardware-based RFID scanning at physical warehouse receiving docks are
  excluded from the current scope and scheduled for subsequent releases.

    \vspace{0.4cm}
    \noindent \textbf{1.5 \hspace{0.2cm} MOTIVATION}

    \vspace{0.25cm}
    The fundamental motivation driving the development of VendorFlow arises from the direct impact that procurement
  efficiency exercises on organizational financial health and supply chain resilience. In industrial environments,
  unexpected delays in acquiring key raw materials or mechanical assemblies directly halt production lines, breach
  client deliverables, and generate substantial financial penalties. Similarly, procuring goods through unverified
  vendors possessing invalid tax credentials incurs legal liabilities, penalties, and forfeited tax credits.
  Establishing a reliable, automated software platform addresses these critical operational vulnerabilities at their
  source.

    Furthermore, commercial enterprise procurement suites like SAP Ariba or Oracle Cloud Procurement carry exorbitant
  licensing costs and require lengthy, complex deployment cycles, making them inaccessible to small and medium-sized
  enterprises. VendorFlow is motivated by the vision of engineering a modern, modular, and accessible alternative
  using open-source full-stack web technologies. The project provides organizations with enterprise-level governance,
  tax accuracy, and deterministic order tracking without the overhead of heavy enterprise software packages.

    \vspace{0.4cm}
    \noindent \textbf{2.1 \hspace{0.2cm} LITERATURE REVIEW}

    \vspace{0.25cm}
    In the context of modern enterprise software engineering, procurement management demands highly responsive,
  auditable, and automated decision-support frameworks capable of coordinating multi-tiered supplier networks.
  Academic literature and foundational textbooks on supply chain management and enterprise architecture emphasize that
  sustainable procurement requires eliminating manual latency, enforcing formal process models, and establishing
  quantitative supplier governance.

    Chopra and Meindl (2016), in \textit{Supply Chain Management: Strategy, Planning, and Operation} (Pearson
  Education), demonstrate that procurement is fundamentally a strategic coordination problem where sourcing decisions
  directly dictate supply chain surplus. The authors emphasize that information asymmetries between buying
  institutions and external suppliers introduce severe operational frictions, including distorted order signals (the
  bullwhip effect), missed delivery schedules, and uncontrolled maverick expenditures. Their theoretical framework
  proves that automating the purchase requisition cycle and centralizing vendor performance metrics significantly
  dampens inventory variability and accelerates cycle fulfillment.

    Monczka, Handfield, Giunipero, and Patterson (2020), in \textit{Purchasing and Supply Chain Management} (Cengage
  Learning), provide a comprehensive examination of the Procure-to-Pay (P2P) process. They establish that manual,
  paper-dependent procurement systems suffer from systematic points of failure, primarily due to the lack of
  procedural verification at the requisition stage and unmonitored vendor onboarding. Monczka et al.\ emphasize the
  absolute necessity of structured vendor rating models, arguing that supplier evaluation must rely on multi-criteria
  quantitative weights rather than periodic subjective assessments to accurately assess commercial risk and ensure
  delivery compliance.

    Van Weele (2018), in \textit{Purchasing and Supply Chain Management: Analysis, Strategy, Planning and Practice}
  (Cengage Learning EMEA), analyzes statutory compliance and risk mitigation in corporate procurement. Van Weele
  highlights that unvetted supplier onboarding introduces legal vulnerabilities, regulatory tax penalties, and supply
  interruptions. The author details that modern corporate governance models mandate systematic pre-qualification,
  verified Know-Your-Customer (KYC) documentation, and immutable audit logs for every transactional approval to
  satisfy internal and statutory audits.

    From a software engineering perspective, Fowler (2018), in \textit{Patterns of Enterprise Application
  Architecture} (Addison-Wesley), establishes that complex enterprise transaction workflows must be governed by formal
  state machine patterns and domain-driven design rather than arbitrary ad-hoc flags. Fowler proves that modeling
  commercial transactions through explicit, deterministic state machines eliminates race conditions, prevents illegal
  state leaps, and provides a transparent architectural foundation for append-only audit histories in transactional
  enterprise systems.

    \vspace{0.4cm}
    \noindent \textbf{2.2 \hspace{0.2cm} EXISTING SYSTEM}

    \vspace{0.25cm}
    \textbf{Conventional Manual and Spreadsheet-Based Systems:} The earliest and still widespread implementations of
  enterprise procurement rely on manual ledger entries, physical requisition slips, and decentralized spreadsheet
  files. While straightforward to set up, their operational reliability depends entirely on individual clerical
  discipline. Studies and industry analyses confirm that because spreadsheets lack multi-user concurrency control,
  automated data validation, and real-time synchronization, organizations frequently experience version conflicts,
  erroneous manual tax calculations, and lost purchasing records. Departmental staff spend excessive time cross-
  referencing past invoices, and off-contract purchases regularly bypass managerial approval.

    \vspace{0.25cm}
    \textbf{Monolithic Legacy ERP Software Suites:} The subsequent generation of procurement software, exemplified by
  massive enterprise resource planning (ERP) suites such as SAP Ariba and Oracle Procurement Cloud, introduced unified
  relational databases for global corporate procurement. While these systems offer comprehensive functionality, they
  are characterized by extreme architectural complexity, slow deployment schedules, rigid user interfaces, and
  exorbitant licensing fees. For small, medium-sized, and growing institutions, these heavy systems present a
  prohibitive total cost of ownership (TCO) and intimidate standard operational staff with steep learning curves.

    \vspace{0.25cm}
    \textbf{Email-Based and Static Document Exchange:} In many digitized mid-tier enterprises, purchase orders are
  created locally as static PDF documents and dispatched via standard email. While eliminating physical paper, this
  approach provides no structured operational feedback loop. Buyers possess no mechanism to verify whether a supplier
  officially acknowledged the order, commenced manufacturing, dispatched the shipment, or attached legitimate tax
  invoices. Crucial procurement metadata remains trapped within individual mailboxes, rendering continuous vendor
  performance appraisal impossible.

    \vspace{0.4cm}
    \noindent \textbf{2.3 \hspace{0.2cm} PROPOSED SYSTEM}

    \vspace{0.25cm}
    To overcome the fragmentation of spreadsheets, the communication blind spots of email workflows, and the excessive
  complexity of monolithic ERP suites, this project presents \textbf{VendorFlow}. The proposed system is architected
  as an agile, full-stack web application developed on the MERN (MongoDB, Express.js, React 19, Node.js) technology
  stack, delivering an accessible, deterministic, and auditable procurement management portal.

    The core innovation of VendorFlow centers on an enforced Finite State Machine (FSM) that governs the complete
  lifecycle of purchase orders across eight discrete phases: \textit{Draft $\rightarrow$ Pending Approval
  $\rightarrow$ Approved $\rightarrow$ Sent $\rightarrow$ Acknowledged $\rightarrow$ Delivered $\rightarrow$ Invoiced
  $\rightarrow$ Closed}. Each state transition is validated against strict role-based access rules, ensuring that
  purchase orders cannot leap stages or be modified without proper authorization. The platform integrates an automated
  computation engine that dynamically calculates itemized subtotals and statutory 18\% Goods and Services Tax (GST)
  additions in real time.

    Furthermore, VendorFlow incorporates a quantitative supplier evaluation engine that algorithmically computes
  composite ratings based on four weighted pillars: Delivery Timeliness (30\%), Product Quality (30\%), Commercial
  Competitiveness (20\%), and Customer Support Responsiveness (20\%). Based on these scores, the system autonomously
  assigns suppliers to standardized performance tiers (\textit{Preferred, Approved, On-Watch, Blacklisted}), providing
  procurement buyers with objective data for contract allocations. Security and accountability are guaranteed via
  Zero-Trust JWT session handling in \texttt{httpOnly} cookies and an immutable audit logging service capturing
  before-and-after state diffs on every transaction.

    \noindent \textbf{2.4 \hspace{0.2cm} SUMMARY}

    \vspace{0.25cm}
    This chapter reviewed the foundational theoretical literature governing enterprise procurement and supply chain
  management, highlighting the strategic necessity of automated coordination and objective supplier oversight. A
  critical analysis of existing systems revealed significant gaps between error-prone manual spreadsheets and overly
  complex, expensive monolithic ERP platforms. The proposed VendorFlow system was introduced as a modern, modular, and
  accessible solution that combines state machine transaction governance, automated statutory tax verification, and
  algorithmic vendor performance tiering to bridge the operational divide in enterprise procurement.

    The architectural framework of VendorFlow adopts a robust, multi-tier client-server paradigm centered around the

  routing, business state verification, and data persistence into cleanly delineated layers as illustrated in

    \begin{enumerate}

  enforced during state transitions to preserve data integrity.

  by Nodemailer and SMTP protocols to automatically generate purchase order dispatch notices, approval requests, and
  supplier onboarding alerts.

    \vspace{0.4cm}
    \noindent \textbf{4.2 \hspace{0.2cm} MODULE DESCRIPTION}

    \vspace{0.25cm}
    The functional architecture of VendorFlow is partitioned into five tightly coupled, highly cohesive functional
  modules:

    \vspace{0.25cm}
    \noindent \textbf{4.2.1 \hspace{0.2cm} Authentication and Role-Based Access Control (RBAC)}

    \vspace{0.15cm}
    This module governs platform security, credential verification, and granular privilege distribution. Incoming
  authentication requests hash submitted passwords using the \texttt{bcryptjs} cryptographic library (utilizing an
  adaptive work factor of 10 salt rounds) and compare the result against persisted hashes. Upon successful
  verification, the module signs a stateless JWT containing the user identity and assigned role (\texttt{Admin},
  \texttt{Buyer}, or \texttt{Vendor}). Downstream endpoints are protected by route guards that inspect token claims
  and immediately terminate unauthorized access attempts with HTTP 403 Forbidden statuses.

    \vspace{0.25cm}
    \noindent \textbf{4.2.2 \hspace{0.2cm} Vendor Onboarding and KYC Management Module}

    \vspace{0.15cm}
    The vendor onboarding subsystem facilitates the complete supplier lifecycle, from initial expression of interest
  to formal accreditation. It provides dedicated interfaces for entering corporate credentials, including company name,
  registered business address, primary contact details, bank accounts, Permanent Account Number (PAN), and 15-
  character Goods and Services Tax Identification Number (GSTIN). The module executes algorithmic format checks
  against statutory tax identifiers and routes onboarding requests through a deterministic approval workflow
  (\texttt{Pending} $\rightarrow$ \texttt{Active} $\rightarrow$ \texttt{Inactive} $\rightarrow$ \texttt{Blacklisted}).

    \vspace{0.25cm}
    \noindent \textbf{4.2.3 \hspace{0.2cm} Purchase Order Lifecycle and FSM Workflow Module}

    \vspace{0.15cm}
    The core transactional engine of the platform is responsible for authoring, approving, dispatching, and
  reconciling purchase orders. Purchase orders contain multi-item line specifications including item descriptions,
  unit prices, ordered quantities, and statutory tax rates. The module automates the financial calculation of item
  sub-totals, statutory 18\% GST, and aggregated gross order totals. All state transitions follow a rigid 8-state
  deterministic Finite State Machine:
    \[
    \text{Draft} \longrightarrow \text{Pending Approval} \longrightarrow \text{Approved} \longrightarrow \text{Sent}
  \longrightarrow \text{Acknowledged} \longrightarrow \text{Delivered} \longrightarrow \text{Invoiced} \longrightarrow
  \text{Closed}
    \]
    Arbitrary state jumps, retrospective modifications of approved items, and unauthorized lifecycle reversals are
  strictly prevented by transition validation guards.

    \vspace{0.25cm}
    \noindent \textbf{4.2.4 \hspace{0.2cm} Supplier Performance Evaluation and Scorecard Engine}

    \vspace{0.15cm}
    To provide data-driven supplier relationship management, this module implements a multi-criteria performance
  evaluation scorecard. Suppliers are evaluated periodically across four fundamental operational pillars:
    \begin{enumerate}
        \item \textit{Quality Rating ($W_1 = 35\%$):} Conformity of delivered supplies against agreed engineering and
  manufacturing specifications.
        \item \textit{Delivery Timeliness ($W_2 = 30\%$):} Adherence to contractually committed delivery dates without
  dispatch delays.
        \item \textit{Pricing Competitiveness ($W_3 = 20\%$):} Adherence to contracted quote rates without unapproved
  cost escalations.
        \item \textit{Compliance and Responsiveness ($W_4 = 15\%$):} Speed of purchase order acknowledgment and
  statutory documentation compliance.
    \end{enumerate}
    The composite rating is calculated by computing the weighted linear combination:
    \[
    Score_{composite} = \sum_{i=1}^{4} (Metric_i \times W_i)
    \]
    Suppliers are automatically categorized into performance tiers (\textit{Preferred}, \textit{Approved}, \textit{On-
  Watch}, or \textit{Blacklisted}), which are visible to procurement officers during order allocation.

    \vspace{0.25cm}
    \noindent \textbf{4.2.5 \hspace{0.2cm} Audit Logging and Notification Engine}

    \vspace{0.15cm}
    To satisfy corporate governance and audit requirements, this module provides an immutable chronological ledger of
  all platform actions. Every state transition, price change, vendor status modification, and approval action
  generates an audit document recording the acting \texttt{userId}, timestamp, affected entity ID, prior state, new
  state, and client metadata. Concurrently, the notification engine broadcasts asynchronous email updates to suppliers
  and buyers regarding critical workflow milestones.

    \vspace{0.25cm}
    \noindent \textbf{5.2.1 \hspace{0.2cm} Authentication and Role-Based Access Control (RBAC)}

    \vspace{0.15cm}
    System security is established via stateless JSON Web Token (JWT) verification combined with role-based guard
  middleware. Incoming requests carry the token in the \texttt{Authorization: Bearer} header. The authentication
  filter decodes the cryptographically signed payload, extracts user claims, and checks them against the endpoint's
  permitted roles (\texttt{Admin}, \texttt{Buyer}, \texttt{Vendor}).

    \begin{footnotesize}
    \begin{verbatim}
    // Security Middleware: JWT Authentication & Role Verification
    const jwt = require('jsonwebtoken');

    const verifyToken = (req, res, next) => {
      const authHeader = req.headers['authorization'];
      const token = authHeader && authHeader.split(' ')[1];
      if (!token) return res.status(401).json({ message: 'Token missing' });

      jwt.verify(token, process.env.JWT_SECRET, (err, decodedUser) => {
        if (err) return res.status(403).json({ message: 'Invalid or expired token' });
        req.user = decodedUser; // { id, email, role }
        next();
      });
    };

    const authorizeRoles = (...allowedRoles) => {
      return (req, res, next) => {
        if (!req.user || !allowedRoles.includes(req.user.role)) {
          return res.status(403).json({ message: 'Access denied: Unauthorized role' });
        }
        next();
      };
    };
    \end{verbatim}
    \end{footnotesize}

    \vspace{0.25cm}
    \noindent \textbf{5.2.2 \hspace{0.2cm} Purchase Order Data Model and Financial Calculation}

    \vspace{0.15cm}
    The purchase order entity enforces referential integrity through Mongoose schema references, encapsulating
  embedded line items with real-time tax calculation. Statutory 18\% GST is computed directly from item subtotals,
  guaranteeing consistent financial records across the lifecycle.

    \begin{footnotesize}
    \begin{verbatim}
    // Mongoose Schema: Purchase Order with FSM States & 18% GST Computation
    const mongoose = require('mongoose');

    const LineItemSchema = new mongoose.Schema({
      description: { type: String, required: true },
      quantity:    { type: Number, required: true, min: 1 },
      unitPrice:   { type: Number, required: true, min: 0 },
      gstRate:     { type: Number, default: 0.18 }
    });

    const POSchema = new mongoose.Schema({
      poNumber:     { type: String, required: true, unique: true },
      vendorId:     { type: mongoose.Schema.Types.ObjectId, ref: 'Vendor', required: true },
      buyerId:      { type: mongoose.Schema.Types.ObjectId, ref: 'User', required: true },
      status: {
        type: String,
        enum: ['Draft', 'Pending Approval', 'Approved', 'Sent',
               'Acknowledged', 'Delivered', 'Invoiced', 'Closed'],
        default: 'Draft'
      },
      items:        [LineItemSchema],
      subtotal:     { type: Number, required: true },
      taxAmount:    { type: Number, required: true },
      grandTotal:   { type: Number, required: true },
      createdAt:    { type: Date, default: Date.now }
    });
    \end{verbatim}
    \end{footnotesize}

    \vspace{0.25cm}
    \noindent \textbf{5.2.3 \hspace{0.2cm} Deterministic State Machine (FSM) Engine}

    \vspace{0.15cm}
    To prevent unauthorized out-of-sequence order processing, state transitions are governed by a deterministic Finite
  State Machine transition lookup table. State transitions that do not match the predefined transition graph are
  rejected before any database updates occur.

    \begin{footnotesize}
    \begin{verbatim}
    // FSM State Transition Lookup Table & Transition Validator
    const VALID_TRANSITIONS = {
      'Draft':            ['Pending Approval'],
      'Pending Approval': ['Approved', 'Draft'],
      'Approved':         ['Sent'],
      'Sent':             ['Acknowledged'],
      'Acknowledged':     ['Delivered'],
      'Delivered':        ['Invoiced'],
      'Invoiced':         ['Closed'],
      'Closed':           []
    };

    const transitionOrderStatus = async (orderId, targetStatus, userId) => {
      const order = await PurchaseOrder.findById(orderId);
      const permitted = VALID_TRANSITIONS[order.status] || [];

      if (!permitted.includes(targetStatus)) {
        throw new Error(`Illegal state transition: ${order.status} -> ${targetStatus}`);
      }

      const previousStatus = order.status;
      order.status = targetStatus;
      await order.save();

      // Record immutable audit entry
      await AuditLog.create({
        entityId: orderId,
        entityType: 'PurchaseOrder',
        userId,
        action: 'STATUS_TRANSITION',
        fromState: previousStatus,
        toState: targetStatus,
        timestamp: new Date()
      });
      return order;
    };
    \end{verbatim}
    \end{footnotesize}

    \vspace{0.25cm}
    \noindent \textbf{5.2.4 \hspace{0.2cm} Supplier Scorecard and Performance Tiering Algorithm}

    \vspace{0.15cm}
    The supplier evaluation module executes a weighted linear scoring model based on four core operational pillars:
  Quality ($W_1 = 35\%$), Delivery ($W_2 = 30\%$), Pricing ($W_3 = 20\%$), and Compliance ($W_4 = 15\%$). The
  algorithm categorizes vendors into distinct operational tiers based on the resulting aggregate score:

    \begin{footnotesize}
    \begin{verbatim}
    // Algorithmic Supplier Performance Tier Assignment
    function evaluateSupplier(metrics) {
      const weights = { quality: 0.35, delivery: 0.30, pricing: 0.20, compliance: 0.15 };

      const aggregateScore =
        (metrics.qualityScore    * weights.quality)  +
        (metrics.deliveryScore   * weights.delivery) +
        (metrics.pricingScore    * weights.pricing)  +
        (metrics.complianceScore * weights.compliance);

      let tier = 'Blacklisted';
      if (aggregateScore >= 85)      tier = 'Preferred';
      else if (aggregateScore >= 70) tier = 'Approved';
      else if (aggregateScore >= 50) tier = 'On-Watch';

      return { aggregateScore: Math.round(aggregateScore * 10) / 10, tier };
    }
    \end{verbatim}
    \end{footnotesize}

    \vspace{0.4cm}
    \noindent \textbf{6.1 \hspace{0.2cm} CONCLUSION}

    \vspace{0.25cm}
    Procurement in many growing organizations still relies heavily on fragmented spreadsheets, unorganized email
  exchanges, and manual paperwork. This lack of structure regularly leads to misplaced orders, delayed vendor
  deliveries, untracked price changes, and difficulty in verifying statutory tax compliance. The primary objective of
  this project was to design and build \textbf{VendorFlow}, a centralized, web-based procurement and supplier
  lifecycle management platform that addresses these operational bottlenecks directly.

    By developing the application using the MERN stack (MongoDB, Express.js, React, and Node.js), the platform
  establishes a structured and auditable environment for both procurement officers and external suppliers. The core of
  the system enforces a strict finite state machine for purchase orders, ensuring that every order progresses
  logically from initial draft creation to approval, vendor acknowledgment, delivery, invoicing, and final closure.
  This deterministic progression eliminates unauthorized status jumps and provides an unalterable audit trail for
  every change made. Furthermore, automating statutory 18\% Goods and Services Tax (GST) calculations inside line
  items removes manual arithmetic errors, while the objective four-pillar supplier evaluation engine gives procurement
  teams clear, quantifiable data to assess vendor reliability instead of relying on subjective impressions.

    Overall, the project demonstrates that small-to-medium enterprises can achieve high transparency, process
  compliance, and operational efficiency without having to invest in bloated, prohibitively expensive enterprise ERP
  suites.

    \vspace{0.4cm}
    \noindent \textbf{6.2 \hspace{0.2cm} CONTRIBUTIONS OF THE PROJECT}

    \vspace{0.25cm}
    The key practical contributions accomplished through this project include:
    \begin{enumerate}
        \item \textbf{Controlled Purchase Order Lifecycle:} Implemented an 8-stage finite state machine that
  guarantees purchase orders can only transition through authorized operational phases, preventing out-of-order
  execution and unapproved modifications.
        \item \textbf{Role-Based Security and Isolation:} Configured stateless JSON Web Token (JWT) authentication
  paired with server-side role validation, granting distinct, protected views and actions for Administrators,
  Procurement Officers (Buyers), and Vendors.
        \item \textbf{Automated Financial and Tax Calculations:} Developed an interactive purchase order builder in
  React that recalculates unit line totals, applies statutory 18\% GST, and updates gross expenditure figures in real
  time as items are adjusted.
        \item \textbf{Objective Supplier Evaluation:} Formulated a weighted scoring algorithm evaluating suppliers
  across Quality (35\%), Delivery Timeliness (30\%), Pricing (20\%), and Compliance (15\%), automatically categorizing
  them into actionable performance tiers (\textit{Preferred, Approved, On-Watch, Blacklisted}).
        \item \textbf{Complete Audit Logging:} Engineered an immutable logging mechanism that records who initiated
  each change, what the prior and updated values were, and the exact timestamp of execution.
    \end{enumerate}

    \vspace{0.4cm}
    \noindent \textbf{6.3 \hspace{0.2cm} LIMITATIONS}

    \vspace{0.25cm}
    While the platform meets its core functional objectives, a few practical limitations remain:
    \begin{itemize}
        \item \textbf{Standalone Operation:} The application currently functions independently and is not yet
  integrated with external enterprise ERP systems (such as SAP or Tally) or external banking payment gateways for
  automated fund transfers.
        \item \textbf{Document Digitization:} Physical invoices and delivery challans currently require manual
  verification rather than being parsed automatically through optical character recognition (OCR).
        \item \textbf{Email-Only Alerts:} Workflow notifications currently rely on SMTP email delivery, with no real-
  time push notifications or SMS alerts implemented for mobile users.
    \end{itemize}

    \vspace{0.4cm}
    \noindent \textbf{6.4 \hspace{0.2cm} FUTURE ENHANCEMENTS}

    \vspace{0.25cm}
    To build upon the foundation established in this project, future development will focus on the following
  enhancements:

        \item \textbf{Automated OCR Invoice Matching:} Introducing optical character recognition (using Tesseract or
  cloud-based document AI) to automatically scan supplier-uploaded invoice PDFs and reconcile line items, quantities,
  and totals directly against the corresponding purchase order (Three-Way Matching).
        \item \textbf{Real-Time WebSocket Updates:} Replacing intermittent polling with bidirectional WebSocket
  connections (via Socket.io) to instantly alert buyers and vendors of order status changes, approvals, and messages

        \item \textbf{Payment Gateway and Accounting API Integration:} Integrating corporate banking APIs or
  accounting software interfaces to allow automated payments once goods receipt notes (GRN) and invoices are fully
  validated.
        \item \textbf{Predictive Spend and Demand Analytics:} Incorporating lightweight time-series forecasting models
  to analyze historical order trends, helping procurement teams anticipate material reorder points and negotiate
  better bulk contract terms with preferred suppliers.
    \end{enumerate}

    exports.updatePOStatus = async (req, res) => {
      try {
        const { id } = req.params;
        const { status: targetStatus, comment } = req.body;
        const userId = req.user.id;

        const po = await PurchaseOrder.findById(id);
        if (!po) {
          return res.status(404).json({ message: 'Purchase order not found' });
        }

        const permittedNextStates = VALID_TRANSITIONS[po.status] || [];
        if (!permittedNextStates.includes(targetStatus)) {
          return res.status(400).json({
            message: `Illegal transition from '${po.status}' to '${targetStatus}'`
          });
        }

        const previousStatus = po.status;
        po.status = targetStatus;
        po.history.push({

          updatedBy: userId,
          comment: comment || `Status updated to ${targetStatus}`,
          timestamp: new Date()

        await AuditLog.create({
          entityId: po._id,
          entityType: 'PurchaseOrder',
          action: 'STATUS_TRANSITION',
          performedBy: userId,
          details: { from: previousStatus, to: targetStatus, comment }
        });

        return res.status(200).json({ success: true, order: po });
      } catch (error) {
        return res.status(500).json({ message: error.message });
      }
    };

    // Computes 4-pillar weighted evaluation and sets vendor tier
    exports.createEvaluation = async (req, res) => {
      try {
        const { vendorId, quality, delivery, pricing, compliance, period } = req.body;

        // Weights: Quality=35%, Delivery=30%, Pricing=20%, Compliance=15%
        const compositeScore = Number(
          (quality * 0.35 + delivery * 0.30 + pricing * 0.20 + compliance * 0.15).toFixed(2)
        );

        let tier = 'Blacklisted';
        if (compositeScore >= 85)      tier = 'Preferred';
        else if (compositeScore >= 70) tier = 'Approved';
        else if (compositeScore >= 50) tier = 'On-Watch';

        const record = await Evaluation.create({
          vendorId,
          evaluationPeriod: period,
          qualityScore: quality,
          deliveryScore: delivery,
          pricingScore: pricing,
          complianceScore: compliance,
          compositeScore,
          tierAssigned: tier,
          evaluatedBy: req.user.id
        });

        // Update vendor aggregate score and tier
        await Vendor.findByIdAndUpdate(vendorId, {
          overallScore: compositeScore,
          tierRating: tier
        });

        return res.status(201).json({ success: true, evaluation: record });
      } catch (error) {
        return res.status(500).json({ message: error.message });
      }
    };
